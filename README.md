# Постановка задачи
Требуется разработать Web приложение - личный кабинет пользователя ML сервиса. Подборка примеров с подобными сервисами - ссылка.

 

## Функциональные требования к личному кабинету

- Главная страница с описанием возможностей ML сервиса
- Возможность зарегистрироваться и авторизоваться
- Возможность просматривать баланс (баланс в условных кредитах)
- Возможность пополнять баланс через кнопку пополнить (эквайринг подключать не требуется)
- Возможность выполнить запрос к ML сервису из Web интерфейса со списанием кредитов с баланса (при условии успешного выполнения запроса)
- Возможность просматривать историю загруженных данных и предсказаний по ним, с указанием суммы списанных кредитов
- Возможность выполнять запросы к ML сервису с помощью REST интерфейса
- Требуется предусмотреть валидацию данных. Если в загружаемой выборке присутствуют ошибочные данные, то возвращать их пользователю, а над валидными данными производить предсказание
- Требуется предусмотреть проверку на положительный баланс при запросах к системе.
- Роль администратор подразумевает возможность пополнять баланс пользователям (модерировать пополнения от пользователей) и просматривать все транзакции. Данное задание является не обязательным и в случае выполнения принесет дополнительные балы.
 

## Этапы выполнения задачи

- Спроектировать объектную модель сервиса. Выделить базовые сущности с которыми будет происходить работа. Пользователь, ML модель, история транзакций/предсказаний, задача для ML модели и т.д. При проектирование написать названия классов, названия полей, методов, принимаемых типов данных, модификаторов доступа. При проектирование использовать все базовые принципы ООП, а именно инкапсуляцию, наследование для расширения классов и полиморфизм. Проектирование допускается в виде написанного кода.
- Подключить к объектной модели приложения базу данных, с использованием ORM фреймворка. Протестировать работоспособность системы, а именно создание пользователей, пополнение баланса, списание с баланса, история транзакций и т.д. Подготовить сценарий инициализации базы данных стандартными данными (демо пользователь, демо администратор, базовые модели доступные для работы).
- Реализовать 2 интерфейса взаимодействия с системой, REST и Telegram bot. Интерфейс должен содержать весь базовый функционал системы: регистрация, авторизация, отправка данных для предсказания, просмотр и пополнение баланса. 
- Реализовать взаимодействие системы с ML сервисом посредством передачи сообщений. Требуется развернуть несколько воркеров, подключить их к RabbitMQ, настроить RabbitMQ в режиме один издатель - несколько слушателей. Воркеры должны получать ML задачу, проводить валидацию данных, выполнять предикт, сообщать результат своей работы. Требуется протестировать работу системы на примере Telegram bot. 
- Требуется разработать Web приложение, которое будет взаимодействовать с ранее построенной системой и реализует весь требуемый функционал. 
- Требуется покрыть ядро системы тестами. Создание пользователей, постановка ML задачи на выполнение, списание баланса и т.д.
- Требуется упаковать все элементы системы в Docker контейнер и развернуть все локально или на внешнем сервере. 
- Требуется настроить систему мониторинга Web приложения, telegram bot, очередей сообщений, работоспособности системы и провести нагрузочное тестирование.

#### Практическое задание №2: Структура проекта и Docker Compose
Контекст задания
Данное задание выполняется на раннем этапе курса и закладывает основу для всех последующих работ. Его цель — привести проект к единому, воспроизводимому виду, пригодному для разработки, запуска и масштабирования.

Студенты должны опираться на:
- пример структуры проекта, разобранный на лекции;
- требования общего задания курса;
- принципы изоляции сервисов и конфигурации через окружение.

Цель работы — научиться:
- правильно структурировать backend-проект;
- описывать инфраструктуру приложения с помощью docker-compose;
- разделять ответственность между сервисами;
- обеспечивать воспроизводимый запуск системы.

После выполнения задания студент должен понимать:
- роль каждого сервиса в системе;
- как сервисы взаимодействуют друг с другом;
- как хранить данные и конфигурацию вне контейнеров.

Требования к структуре проекта -  Структура проекта должна соответствовать примеру, разобранному на лекции.

Минимально ожидаемая структура (пример):

project-root/

├── app/

│ ├── src/

│ ├── Dockerfile

│ └── .env

├── web-proxy/

│ ├── nginx.conf

│ └── Dockerfile

├── docker-compose.yml

└── README.md

Допускаются отличия в деталях, если логика структуры сохранена.

Общая архитектура сервисов
В рамках задания требуется поднять 4 сервиса:
- app — backend-приложение;
- web-proxy — reverse proxy (Nginx);
- rabbitmq — брокер сообщений;
- database — база данных PostgreSQL.

Все сервисы должны быть описаны в одном docker-compose.yml файле.

Требования к сервисам
1. Сервис app

Требования:
конфигурирование через переменные окружения;
использование env_file для передачи настроек;
исходные файлы приложения подключаются через volumes;
сервис не должен пробрасывать порты наружу напрямую;
взаимодействие с внешним миром происходит через web-proxy.

2. Сервис web-proxy

Требования:
создаётся на основе образа Nginx;
зависит от сервиса app (depends_on);
проксирует HTTP-запросы к app;
пробрасывает наружу порты:80;443;
конфигурация Nginx хранится в проекте.

3. Сервис rabbitmq

Требования:
создаётся на основе образа rabbitmq;
пробрасывает наружу порты:5672 (AMQP);15672 (management UI);
используется volume для хранения данных:локальная директория → /var/lib/rabbitmq внутри контейнера;
данные очередей должны сохраняться после перезапуска;
установлен параметр автоматического перезапуска при сбоях (restart).

4. Сервис database

Требования:
создаётся на основе образа postgres;
конфигурация через переменные окружения;
используется volume для хранения данных базы;
данные должны сохраняться при удалении контейнера.
Требования к docker-compose.yml
Файл docker-compose.yml должен:

описывать все 4 сервиса;
использовать depends_on для описания зависимостей;
использовать volumes для хранения данных;
использовать env_file для сервиса app;
быть валидным и запускаться командой:
docker compose up

Пошаговый план выполнения задания
- Шаг 1. Создание структуры проекта
Создать директории сервисов;
Подготовить базовые Dockerfile (если требуется).
- Шаг 2. Описание сервиса app
Настроить env_file;

- Шаг 3. Настройка web-proxy
Подготовить конфигурацию Nginx;

Проверить доступ по порту 80.
- Шаг 4. Подключение RabbitMQ
Добавить сервис rabbitmq;
Настроить проброс портов;
Проверить доступ к management UI.
- Шаг 5. Подключение базы данных

Настроить volume для хранения данных;

- Шаг 6. Финальная проверка
Запустить все сервисы;
Убедиться, что контейнеры стартуют без ошибок;
Проверить взаимодействие сервисов между собой.


Критерии оценки
- Соответствие структуры проекта примеру с лекции;
- Корректность docker-compose.yml;
- Выполнение всех требований к сервисам;
- Использование volumes и env_file;
- Возможность воспроизводимого запуска проекта.


## Быстрый старт

1) Создайте локальный `.env` на основе шаблона:

```bash
cp .env.example .env
```

2) Запустите сервисы:

```bash
docker compose up --build
```

- Nginx: http://localhost (порт 80)
- RabbitMQ UI: http://localhost:15672 (логин/пароль из .env)
- Postgres: localhost:5432

> В репозиторий коммитим только `.env.example`, файл `.env` должен оставаться локальным и находится в `.gitignore`.

#### Практическое задание №3: Подключение базы данных и ORM
Контекст задания

Данное задание является продолжением задания по проектированию объектной модели. К этому моменту у студента уже должна быть:
- спроектирована объектная модель предметной области;
- описаны основные сущности и их связи;
- заложена бизнес-логика сервиса.

Теперь требуется связать объектную модель с реальным хранилищем данных с использованием ORM-фреймворка.


Цель работы — научиться:
- применять ORM для отображения объектной модели на реляционную базу данных;
- проектировать таблицы на основе доменных сущностей;
- обеспечивать сохранность и целостность данных;
- проверять бизнес-логику через работу с БД.

После выполнения задания студент должен понимать:
- как объектная модель превращается в структуру БД;
- как ORM управляет сохранением и загрузкой данных;
- какие операции должны быть атомарными и транзакционными.

Общие требования

При выполнении задания необходимо:
- использовать объектную модель, разработанную на первом уроке;
- не изменять бизнес-смысл сущностей без обоснования;
- использовать ORM-фреймворк (например: SQLAlchemy, SQLModel);
- использовать реляционную базу данных (PostgreSQL рекомендуется);
- хранить конфигурацию подключения к БД в переменных окружения.

Требования к моделям и БД

1. Отображение сущностей в БД
Для каждой ключевой сущности объектной модели должна быть:
- соответствующая таблица в базе данных;
- первичный ключ;
- корректные типы данных;
- связи между таблицами (Foreign Key).

Минимально должны быть реализованы таблицы:
- пользователей;
- ML-моделей;
- истории ML-запросов / предсказаний.

2. Работа с пользователями
Необходимо реализовать и протестировать:
- создание пользователя;
- загрузку пользователя из БД;
- связь пользователя с балансом и историей.

3. Работа с балансом и транзакциями
Требуется реализовать:
- пополнение баланса;
- списание кредитов;
- проверку баланса перед списанием;
- сохранение каждой операции в истории транзакций.

4. История запросов пользователя
Необходимо обеспечить возможность:
- получения истории предиктов пользователя;
- сортировки по дате;
- отображения суммы и связанной сущности (ML-задачи, если применимо).

Инициализация базы данных 
Требуется подготовить сценарий начальной инициализации БД, который создаёт:
- демо-пользователя;
- начальный баланс для пользователей;
- набор базовых ML-моделей, доступных для работы.

Инициализация должна:
- выполняться автоматически;
- быть идемпотентной (повторный запуск не ломает данные);

Пошаговый план выполнения задания

Шаг 1. Подключение ORM
- Подключить ORM к проекту;
- Настроить соединение с БД через env-переменные.
Шаг 2. Описание ORM-моделей
- Описать таблицы на основе объектной модели;
- Настроить связи между сущностями.
